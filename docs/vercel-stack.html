The Vercel stack behind The AI Wire

One small app, nine platform features. The AI Wire is a personal AI newsroom — it ingests RSS feeds, writes articles with an LLM, routes drafts past a human, and publishes to news.baeke.info. This guide walks through every Vercel component it leans on, with the actual code from this repo and links to the official docs, so the project doubles as a Vercel curriculum.

№ 02

The web app — Next.js on Vercel

zero-config framework hosting · React Server Components · Server Actions

Vercel detects Next.js from package.json and needs no build configuration at all — notice this repo's next.config.mjs is an empty object and there's no build setup in vercel.json. Every part of the framework maps to platform infrastructure automatically: pages become prerendered assets or functions, API routes become functions, middleware runs in front of the cache.

Server Components

Every page here is a React Server Component — app/page.tsx is an async function that queries Postgres directly and returns JSX. No client-side data fetching, no API layer for reads, almost zero JS shipped to readers.

Server Actions

The review desk mutates data with Server Actions ('use server' files) — Approve, Rewrite, Decline are plain async functions wired to forms. Vercel runs them as function invocations; there are no hand-written POST endpoints for the UI.

Middleware

middleware.ts guards /review/* with a cookie check and redirects to the login page. It runs before routing and caching, on every matched request.

Middleware as an auth gate

middleware.tsruns before every /review request
export async function middleware(req: NextRequest) {
  if (req.nextUrl.pathname.startsWith('/review/login')) return NextResponse.next();

  const cookie = req.cookies.get(REVIEW_COOKIE_NAME);
  const expected = password ? await reviewSessionToken(password) : null;
  if (!expected || cookie?.value !== expected) {
    const url = req.nextUrl.clone();
    url.pathname = '/review/login';
    return NextResponse.redirect(url);
  }
  return NextResponse.next();
}

// only run on the review desk — public pages skip the gate entirely
export const config = { matcher: ['/review/:path*'] };
Learn this

The rendering decision is per-route, chosen in code: the home page opts into dynamic rendering (dynamic = 'force-dynamic') because filters and pagination read searchParams, while article pages use ISR (revalidate = 300) because they change rarely. Same app, two strategies — see section 11.

№ 03

Vercel Functions & Fluid compute

route handlers become functions · maxDuration · one function is the whole backend worker

Every route.ts under app/api/ deploys as a Vercel Function. There is no server to provision: you export an HTTP-method handler, and the platform gives you scale-to-zero compute. Since Fluid compute became the default, functions run full Node.js, instances are reused across concurrent requests (dramatically fewer cold starts), and billing is based on active CPU time rather than wall-clock.

This project's entire ingestion/writing pipeline is one function. The interesting bits are the two config exports at the top:

app/api/tick/route.tsthe newsroom worker
export const runtime = 'nodejs';   // full Node.js — pg, Buffers, crypto all work
export const maxDuration = 300;    // give the pipeline up to 5 minutes per invocation

export async function POST(req: NextRequest) {
  if (!isAuthorized(req.headers.get('authorization'))) {
    return NextResponse.json({ error: 'unauthorized' }, { status: 401 });
  }

  if (req.nextUrl.searchParams.get('ingest') === '1') {
    ingested = await ingestFeeds();     // pull RSS feeds, insert new articles
  }

  const processed = await runTick();   // loop: claim article → run handler → repeat
  if (processed.some((p) => p.to === 'published')) {
    revalidatePath('/');               // something went live → bust the cache
  }
  return NextResponse.json({ ingested, processed });
}

Inside, runTick() respects a time budget (240s by default, tunable via TICK_BUDGET_MS) so it always finishes inside maxDuration instead of being killed mid-article:

lib/tick.tsbudget-aware work loop
const deadline = Date.now() + budgetMs;   // 240_000 < maxDuration of 300s

while (Date.now() < deadline) {
  const article = await claimNext();      // FOR UPDATE SKIP LOCKED — see §7
  if (!article) break;                    // queue empty → stop early, pay less
  const to = await handler(article);      // scrape / tag / write / thumbnail
}
Why this matters on Hobby

Default function timeout is generous now (up to 300s+ with Fluid compute even on Hobby), but you still declare intent with maxDuration. The lighter /api/ingest route declares maxDuration = 60 — right-size each function rather than maxing everything out. Also note what's absent: no runtime = 'edge' anywhere. Node.js on Fluid compute is the recommended default; Edge is legacy.

Cron jobs — and their Hobby-plan workaround

vercel.json crons · CRON_SECRET auth · GitHub Actions as the fast scheduler

Vercel Cron is declarative: list paths and schedules in vercel.json (or vercel.ts), and after each deploy Vercel invokes those paths on schedule. The entire config here is five lines:

vercel.jsonthe whole platform config for this project
{
  "crons": [
    { "path": "/api/tick?ingest=1", "schedule": "0 6 * * *" }
  ]
}

But there's a plot twist: the newsroom wants a tick every 5 minutes, and Hobby-plan cron jobs are limited (low count, roughly once-per-day granularity, imprecise timing). So the daily Vercel cron is only the backstop, and the real scheduler is a GitHub Actions workflow calling the same endpoint — an instructive pattern: any scheduler works, as long as the work lives in a Vercel Function behind a shared secret.

Scheduler A — GitHub Actions, every 5 min
# .github/workflows/tick.yml
on:
  schedule:
    - cron: '*/5 * * * *'
jobs:
  tick:
    steps:
      - run: |
          curl -sf -X POST \
            -H "Authorization: Bearer ${{ secrets.CRON_SECRET }}" \
            "${{ secrets.APP_URL }}/api/tick?ingest=1"
Shared gate — timing-safe secret check
// lib/auth.ts — both schedulers present the same header
import { timingSafeEqual } from 'node:crypto';

export function isAuthorized(headerValue) {
  const expected = `Bearer ${process.env.CRON_SECRET}`;
  // constant-time compare — no secret leakage via timing
  return timingSafeEqual(Buffer.from(headerValue), Buffer.from(expected));
}
Learn this

Vercel sends Authorization: Bearer <CRON_SECRET> automatically when a CRON_SECRET env var exists on the project — so one auth check covers Vercel Cron, GitHub Actions, and the “Run tick now” button on the review desk. Cron invocations are visible under the project's Settings → Cron Jobs tab, and each run is a normal function invocation in the logs.

№ 05

AI Gateway — every model, zero API keys

"provider/model" strings · OIDC auth · text, structured output, and images through one door

This is the most modern piece of the stack. The app calls three different AI capabilities — prose writing, structured tagging, image generation — across two providers (DeepSeek and Google), and holds zero provider API keys. The AI SDK (ai package) treats a plain "provider/model" string as a model routed through the Vercel AI Gateway, which authenticates with the deployment's OIDC token, handles billing centrally, and gives you per-model observability in the dashboard.

Unified API

Swap providers by changing an env var — TEXT_MODEL=deepseek/deepseek-v4-flash, IMAGE_MODEL=google/imagen-4.0-fast-generate-001. No SDK changes, no new keys.

OIDC auth

On Vercel, VERCEL_OIDC_TOKEN is injected automatically. Locally, vercel env pull refreshes it. Non-Vercel environments can use an AI_GATEWAY_API_KEY instead.

Cost control

The gateway dashboard showed thumbnails were ~95% of spend — switching IMAGE_MODEL from Gemini image ($0.067) to Imagen 4 Fast ($0.02) was a one-line fix.

All three call shapes, one file

lib/llm.tsthe app's entire AI surface (trimmed)
import { generateText, generateObject, generateImage, jsonSchema } from 'ai';

// 1 — free-form prose (article drafts). Model id is just a string.
const { text } = await generateText({
  model: process.env.TEXT_MODEL ?? 'deepseek/deepseek-v4-flash',
  system, prompt: user,
});

// 2 — structured output (tags, review verdicts) validated against a JSON schema
const { object } = await generateObject({
  model: textModel(),
  system: system + keyHint,          // spell out property names — see gotcha below
  prompt: user,
  schema: jsonSchema<T>(schema),
});

// 3 — image generation (thumbnails), with a fallback for chat-style image models
try {
  const { image } = await generateImage({ model, prompt });
  return Buffer.from(image.uint8Array);
} catch (imageApiErr) {
  // Multimodal chat models (e.g. gemini-flash-image) don't speak the image API;
  // they return images as files on a generateText result.
  const result = await generateText({ model, prompt });
  const image = result.files.find((f) => f.mediaType?.startsWith('image/'));
  if (!image) throw imageApiErr;
  return Buffer.from(image.uint8Array);
}
Field notes from this project

Cheap models cut corners. DeepSeek v4-flash occasionally invents its own JSON property names despite the schema, so structured() validates required keys itself, spells the keys out in the prompt, and retries once. jsonSchema() alone does not deep-validate at runtime — defensive coding around model output is part of the craft.

Testing costs $0. FAKE_LLM=1 short-circuits all three functions with canned outputs; the entire test suite runs the real pipeline without a single gateway call.

Vercel Blob — thumbnails without a bucket

object storage with a two-line API · public URLs served from Vercel's CDN

Generated thumbnails need to live somewhere. Instead of wiring up S3 (IAM, buckets, signed URLs…), the project uses Vercel Blob: add the store to the project, and it injects BLOB_READ_WRITE_TOKEN; upload with put(), get back a CDN-served public URL, store that URL in Postgres. That's the whole integration:

lib/handlers/thumbnail.tsimage model → Blob → database
import { put } from '@vercel/blob';

const imageBuffer = await generateImage(prompt);           // via AI Gateway, §5
const blob = await put(
  `thumbnails/${article.id}-${Date.now()}.png`,          // pathname inside the store
  imageBuffer,
  { access: 'public', contentType: 'image/png' }
);
thumbnailUrl = blob.url;   // permanent public URL — saved to the articles row

Note the resilience pattern around it: if generation or upload fails, the handler falls back to an inline SVG placeholder (placeholderSvgDataUrl) rather than failing the article. The pipeline keeps moving; a human can request a new image from the review desk later.

Learn this

Blob supports access: 'public' (anyone with the URL, served via CDN — right for article thumbnails) and private storage for content that needs authorization. Filenames here include Date.now() so a regenerated thumbnail gets a fresh URL and never fights browser/CDN caches over a stale object.

№ 07

Neon Postgres via the Vercel Marketplace

first-party databases are gone — the Marketplace is the pattern · pooled connections for serverless

Vercel no longer runs its own Postgres/KV; databases come from the Marketplace. Installing the Neon integration provisions a free-tier Postgres, injects the pooled DATABASE_URL into the project's env, and unifies billing under the Vercel account. The app talks to it with vanilla pg — no ORM, no Vercel-specific client:

lib/db.tsthe entire database layer
import { Pool } from 'pg';

let pool: Pool | null = null;

export function getPool(): Pool {
  if (!pool) {
    // module-level singleton — Fluid compute reuses the instance across
    // requests, so warm invocations reuse these connections too
    pool = new Pool({ connectionString: process.env.DATABASE_URL, max: 5 });
  }
  return pool;
}

The database is also the job queue. Because the worker might be invoked concurrently (GitHub Actions + Vercel Cron + the review-desk button), claiming work must be race-free. Postgres does this natively:

lib/claim.tsa queue in one SQL statement
UPDATE articles SET claimed_at = now()
WHERE id = (
  SELECT id FROM articles
  WHERE status = ANY($1)                -- any status that has a handler
    AND (claimed_at IS NULL
         OR claimed_at < now() - interval '10 minutes')  -- stale-claim recovery
  ORDER BY updated_at ASC
  LIMIT 1
  FOR UPDATE SKIP LOCKED                -- concurrent tickers never grab the same row
)
RETURNING *
Why “pooled” matters

Serverless functions can fan out to many instances, and each pg.Pool opens real connections. Neon's pooled connection string puts PgBouncer in front of Postgres so hundreds of short-lived function connections don't exhaust the database's connection limit. Rule of thumb on Vercel: always use the pooled URL from serverless code, keep the direct URL for migrations.

Environment variables & the OIDC token

vercel env pull · per-environment values · secrets that never live in git

Configuration flows one way: Vercel is the source of truth, and local dev pulls from it. Integrations (Neon, Blob) inject their own vars; you add the app-specific ones; then vercel env pull materializes a local snapshot — including a fresh VERCEL_OIDC_TOKEN, which is how local dev talks to the AI Gateway without keys.

This repo's .env.local deliberately points DATABASE_URL at the local Docker Postgres. A “production” migration once silently ran against localhost, and the deployed site 500'd with relation does not exist. The fix that's now doctrine here:

Git integration — deployment is a push

push to master → production · every branch → preview URL · no CI pipeline to maintain

There is no deploy script in this repo. The Vercel project is connected to github.com/gbaeke/vercel-news, so every push to master builds and ships to production, and every push to any other branch gets an isolated preview deployment with its own URL — same build, same env (preview-scoped), shareable before merging.

What a push triggers
  • Vercel clones the commit and runs next build (framework auto-detected)
  • Pages, functions, and middleware are provisioned from the build output
  • The deployment gets an immutable URL (vercel-news-<hash>.vercel.app)
  • On master: production aliases (news.baeke.info) atomically switch to it
  • Instant rollback = re-aliasing to any previous immutable deployment
Project link on disk
// .vercel/project.json — created by `vercel link`,
// ties this folder to the cloud project for CLI commands
{
  "projectId": "prj_lqlzUcPJ…",
  "orgId": "team_aySWArGa…",
  "projectName": "vercel-news"
}
Field note

With the Git integration active, don't also run vercel deploy manually — you get duplicate builds of the same commit. The CLI is still useful for everything else: vercel env pull, vercel logs, vercel inspect.

Custom domains & DNS

news.baeke.info · CNAME to a per-project target · automatic TLS

The site ships on vercel-news-three.vercel.app for free, but the real address is news.baeke.info. Adding a domain is two steps: declare it on the Vercel project (dashboard or vercel domains add), then create the DNS record Vercel asks for at your DNS host. Vercel then provisions and renews TLS certificates automatically.

This project's DNS setup
  • Zone baeke.info lives on Cloudflare (not Vercel DNS)
  • news is a CNAME → 165523850bfbfe44.vercel-dns-017.com — a per-project target, safer than the shared cname.vercel-dns.com
  • Record is DNS-only (un-proxied): Cloudflare's orange-cloud proxy in front of Vercel's proxy causes TLS/redirect weirdness — let Vercel terminate
  • A wildcard *.baeke.info → Azure exists; the specific news record overrides it
Verify from the terminal
$ dig +short news.baeke.info CNAME
165523850bfbfe44.vercel-dns-017.com.

$ curl -sI https://news.baeke.info | head -3
HTTP/2 200
server: Vercel
x-vercel-cache: HIT
Learn this

Apex domains (baeke.info itself) can't be CNAMEs — for those you'd use Vercel's A record (or move nameservers to Vercel DNS). Subdomains like news. are the easy case. Domain assignments follow the production deployment: every push to master re-points the domain atomically, and preview deployments never touch it.

Caching & ISR — publish means revalidate

two rendering strategies in one app · time-based + on-demand revalidation

The app demonstrates the two revalidation modes working together on the same content:

Time-based (ISR)
// app/articles/[slug]/page.tsx
export const revalidate = 300;

Article pages are served from Vercel's cache and re-generated in the background at most every 5 minutes. Readers get static-page speed; the database is barely touched.

On-demand (event-driven)
// on approve, and after any tick that publishes
revalidatePath('/');
revalidatePath('/articles/[slug]', 'page');

The moment an article goes live — via the Approve button or the tick worker — the caches are purged so the wire updates instantly instead of waiting out the timer.

Meanwhile the home page opts out of caching entirely (dynamic = 'force-dynamic') because tag filters and pagination come from searchParams. That's the decision framework to internalize: static + revalidate when content changes rarely; on-demand revalidation when you know the exact moment it changes; dynamic when every request is different. You can watch it working via the x-vercel-cache response header (HIT / STALE / MISS).

What this project deliberately does NOT use — and what to explore next
  • Edge runtime — intentionally absent. Node.js on Fluid compute is the modern default; reach for Edge basically never.
  • Vercel Queues — the Postgres status column + SKIP LOCKED is the queue. At larger scale, Queues (durable, at-least-once delivery) would replace it.
  • Workflow DevKit — the tick loop is stateless and restartable, so plain functions suffice. Long multi-step jobs that must survive crashes would want Workflow.
  • vercel.ts — this repo still uses vercel.json; the newer typed config via @vercel/config is a natural upgrade.
  • Observability, Firewall, BotID — worth a tour of the dashboard tabs even on Hobby: request logs, WAF rules, and bot filtering all apply to this app unchanged.
